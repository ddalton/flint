flint-passthrough: the FlintPassthroughMount CRD is installed.

Mounts are delivered by the s3.csi.chert.us CSI node driver (chart
flint-s3-csi); nothing in THIS chart runs. Declare a mount in the
namespace of the pods that will use it:

  apiVersion: chert.us/v1alpha1
  kind: FlintPassthroughMount
  metadata: { name: datasets }
  spec:
    bucket: my-bucket
    keyPrefix: datasets/imagenet
    endpoint: http://minio.flint-system.svc:9000   # unset => AWS S3
    readOnly: true
    uid: 1001                                       # the mount's owner
    consumers:
      serviceAccounts: [trainer]                    # ABSENT = nobody
    # identity.mode: broker (default) | webIdentity | static | ambient

Then give a pod the mount as ONE volume:

  spec:
    serviceAccountName: trainer
    volumes:
      - name: data
        csi:
          driver: s3.csi.chert.us
          volumeAttributes: { chert.us/mount: datasets }
    containers:
      - volumeMounts: [{ name: data, mountPath: /mnt/s3 }]

A pod naming a CR that does not exist, or whose ServiceAccount is not a
consumer, stays ContainerCreating with a FailedMount event that names
the reason.

OWNERSHIP AND MODES ARE FIXED AT MOUNT, and the bucket stores neither.
Every file shows the mount's owner (the volume's chert.us/uid, else
spec.uid, else 65534) and mount-s3's modes: 0644 for files, 0755 for
directories, unless spec.mountOptions passes --file-mode/--dir-mode.
chmod, chown and chgrp on an existing file fail with EPERM; on a file
still being written they succeed and change nothing. touch fails on an
existing file the same way. So chmod +x cannot make a script
executable: only --file-mode can, and then for every file.
