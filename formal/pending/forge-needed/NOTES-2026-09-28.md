# The rewind fix (2026-09-28)

**The rule, now in the model:** `RestoreDropsNamedRetention`. A restore
takes every pack the snapshot names out of `retained` (a named pack is
not on its way out). `ForgeSyncRewind.tla` md5 5ee1b260; FALSE is the
09-27 model, kept as the mutation.

**Why the 09-27 counterexample is a real loss, not only the witness.**
Its last state has `holds[f1] = {}` and `main = p1`. s1's fold dropped
p1 while its commit was rewound, so f1 does not hold it. p1 is named
again only because s2's needed listing named the re-pushed pack. s1's
next batch names `belief.packs \ retained = {f1}`, so `main` rests on
no named pack, and retention then unlinks p1.
`ForgeSyncRewindKeepsNamedRetentionLoss` (no proof witness) is the
check that this loss is reached.

**The shipped code does not reach it.** It needs `FoldReachableCoverage`
(a serving fold drops an input whose uncovered objects no ref reaches).
The shipped fold drops an input only when the roll-up holds all of its
objects, so un-naming a retained pack loses nothing. The restore-time
reclaim unlinks instead of retaining (`ReclaimUnlinks`). And
`fold::unlink_retained` already keeps a named pack on the disk. The
rule is a **requirement of the needed-packs design**. In code it is
`restore.rs`: after the snapshot is loaded, drop from `sc.retained`
every name in `cell.snap.packs`, then `save_retained`. Build it with
needed-packs, test-first.

**Generator trap fixed.** `gen.sh` builds these worlds from the gated
`../../ForgeSync*.cfg`, which moved to the shipped baseline on 09-27.
A regeneration would have silently turned the five shipped rules ON
here. It now pins them OFF, as the sandbox was run. Moving the sandbox
onto the shipped rules is a separate step. The regenerated Needed cfgs
are byte-identical to the ones run. The Rewind cfgs differ only by the
new constant.
