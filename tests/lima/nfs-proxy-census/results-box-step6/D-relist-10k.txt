== why: one backoff over every watch
kube-runtime 3.0 Controller::run wraps the merged trigger streams in ONE
StreamBackoff (controller/mod.rs: StreamBackoff::new(self.trigger_selector,
self.trigger_backoff)). On any watcher error it sleeps before polling ANY
watch again: DefaultBackoff, exponential 0.8 s -> 30 s with jitter, reset
only after 120 s without errors. The connection errors while the apiserver
was down had already pushed it to the cap, so each 410 cost ~35-45 s of
total watch silence, and the re-lists could not start until the last 410
had drained. A watch that resumed cleanly then aged out while unread.

== what the old rig got wrong (all three now fixed in step6-box-fleet.sh)
- it waited 180 s; the operator's re-list began at +240 s;
- it read the lifetime VmHWM, already 294 MiB from the initial sync;
- it grepped `kubectl logs` (current file only) for "410|too old|...":
  the operator logged only "event queue error" (the 410 was in the error's
  source chain), and a bare "410" matched a log timestamp instead.
