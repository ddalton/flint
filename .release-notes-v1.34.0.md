## [1.34.0] - 2026-08-20

### Added — the disk-sizing release (flint-lite operator)

Sizing a share's PVC used to be a guess that had to be right the first
time. Kubernetes grows a claim and never shrinks one, so an
over-provisioned project stayed over-provisioned and the only escape
was deleting the share — a poor trade anywhere storage is expensive.
This release makes the disk a decision you can revise in both
directions, and makes the numbers you would revise it against visible.

- **`persistence.autoExpand`** (`enabled`, `bufferPercent` default 100,
  `maxSize` **required**): grow the claim to fit the project rather
  than guessing up front. The size comes from the hub's manifest — the
  project's logical bytes plus headroom, never below the largest single
  object. Growth is an ordinary in-place expansion: same PVC, no data
  movement, no outage.

  **The operator does not write `spec`.** The computed target rides an
  annotation and records the `persistence.size` it was derived from, so
  editing `size` always wins and discards the target. Without that
  basis, "the operator grew past spec" and "the user wants something
  smaller" are the same state and a user could never shrink again.

  `maxSize` is required when enabled, at admission: expansion cannot be
  undone without a reprovision, so an unbounded rule is a bill nobody
  agreed to. At the ceiling the share says so in `PersistenceCurrent`
  instead of quietly stopping.

- **`persistence.reprovisionOnShrink`**: honour a smaller
  `persistence.size` by rebuilding the disk — verify the bucket can
  restore the tree, release the claim, create a new one, import. Reuses
  the hibernate rung's verify-then-delete rather than inventing a
  second way to destroy a volume: the operator holds no bucket
  credentials, so it cannot check recoverability itself and must ask
  the hub. Refused for a share with no `bucket` (its PVC is the only
  copy, so this would be a delete dressed as a resize) and for an
  adopted `existingClaim`. New `Reprovisioning` phase; the wake it
  costs carries the same contract as waking from `Hibernated` — fresh
  `serverId`, so every client remounts.

  **Not abortable by `flint.io/requested-at`**, deliberately, and this
  is the one place it diverges from hibernation. Hibernation comes down
  for want of interest, so interest is a real reason to stop; a rebuild
  was asked for explicitly, and the front door's own keepalive is not a
  change of mind. Aborting on it would make the feature unusable on
  precisely the shares anyone uses.

- **The two features cannot fight.** A shrink that auto-expand would
  simply grow back is refused with its reason, rather than spending an
  outage and a DR import to end up where it started. Decidable from
  spec alone — bring `autoExpand.maxSize` down to the size you want and
  the shrink goes through.

- **`/status` reports what the project costs to hold**: `logicalBytes`
  (the sum — what a full warm fill would pull) and
  `largestObjectBytes` (the max — the PVC's hard floor). They answer
  different questions. The floor is a correctness bound: below it the
  project contains files that can never be read here. Everything above
  it is an economics choice about how much object-store round trip you
  want to pay for. Both are `Option` and never zeroed — a hub that has
  not read a manifest does not know, and reporting 0 would say "empty
  project" to the one reader whose job is to size a disk.

### Fixed

- **An object bigger than the PVC hung the read forever.** The demand
  hydration lane could not tell "no room right now" from "no room
  ever": `admit_hydration` answered both with false and the restore
  loop treats false as *wait*. For an object larger than the volume
  minus its reserve that wait can never end — eviction reclaims only
  what is already local. The marker stayed set, every content lane
  answered `NFS4ERR_DELAY`, and a hard mount hung with no error, no
  counter and no condition. Now refused at request time with
  `NFS4ERR_NOSPC`, counted, and surfaced as a `HydrationUnblocked`
  condition naming the size to raise the claim past. `hydrate::request`
  now returns a `#[must_use]` verdict, so the compiler enumerated every
  caller rather than leaving the set to inspection: both READ lanes,
  WRITE, the SETATTR size lane, and the perfops helper behind
  COPY/CLONE/ALLOCATE/DEALLOCATE.

- **The operator read the hub's tier gauges from the wrong path** —
  top level rather than under `tier`. Every field is
  `#[serde(default)]`, as it must be so an older hub's missing fields
  do not fail the parse, which means a wrong path deserializes cleanly
  and yields `None` forever. `HydrationUnblocked` reported a vacuous
  `True` without ever having looked, and auto-expand would have shipped
  inert. Found only on a live cluster. Now pinned by a test against a
  real captured `/status` document.

- **Failure and boot shed load instead of adding it** (1.33.0
  follow-up): `error_policy` backs off 30s → 900s per consecutive
  failure and clears on success, and `Pending`/`Starting` stops
  requeueing at a flat 15s forever. Both jittered.

### Formal

`FlintShareDisk.tla` — the ladder over one share's PVC, six states
against four independent event sources. The gate is now **181 runs**.

Two findings worth repeating. **The `rpoClean` poll is not what makes
the delete safe — the drain is**: with the drain intact, dropping the
poll gate entirely loses nothing, so there is deliberately no
`NoVerify` run and anyone "optimising" the pod-gone wait because the
poll already said clean would delete a live project's disk. And the
module ships with a **vacuity probe**: its first configuration made
every rebuild unreachable, so the shrink theorem passed by never
firing while the strict run looked identical.

### Upgrade notes

- **CRD schema version 2 → 4.** The self-bootstrap refuses to
  downgrade a newer schema, so a mixed-version fleet is safe — but a
  1.33.0 operator does not know `Reprovisioning`, and `status.phase`
  is a schema enum.
- **`autoExpand` needs a StorageClass with `allowVolumeExpansion:
  true`.** Without it the API server refuses the resize; the share
  reports `ExpansionRefused` and keeps its current disk. kind's default
  `standard` class ships with expansion OFF.
