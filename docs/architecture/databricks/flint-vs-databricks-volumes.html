The question. Databricks gives its users POSIX paths over object storage through FUSE — /Volumes for Unity Catalog volumes, /Workspace for workspace files, /dbfs for the legacy DBFS — and that covers much of what flint's front ends exist to provide. How does it mount the buckets? Is the daemon a sidecar, a CSI node driver, or something else? Does Databricks run on Kubernetes, and does any of it run on-premises? What carries over to flint, and what does not?

The short answer

1 / 9 · delivery

Databricks' FUSE support is a feature of its managed service: the mounts exist only on compute Databricks provisions and runs, and there is no Databricks FUSE client for your own machines. On classic compute the daemons are started by Databricks' own runtime inside its container — neither a sidecar nor a CSI driver. Where Databricks does run Kubernetes, for serverless, the one CSI driver it has described serves local disk, not a bucket. flint does the Kubernetes-native thing: a CSI node plugin makes the mount, and a worker pod serves it.

Where Databricks compute runs

2 / 9 · Kubernetes and on-premises

Databricks runs on Kubernetes in some shapes and not in others, and none of it runs on-premises. Classic compute on AWS and Azure is documented as VMs with a host address and a container address. Classic compute on Google Cloud ran on GKE from its 2021 launch until GKE-based compute was deprecated on 2025-03-17 in favour of GCE VMs. Serverless compute runs on Kubernetes in Databricks' own account, each customer pod in a Kata Containers micro-VM. Databricks' own services run on Kubernetes on all three clouds.

A classic Databricks node

3 / 9 · anatomy

One classic node carries three FUSE trees, a Spark runtime that uses none of them, and — on standard access mode — a sandbox per user. Unity Catalog, in the control plane, is where a volume's permissions and credentials come from. The one box on the page nobody outside Databricks can draw with confidence is the one this document is about: the /Volumes daemon, drawn dashed.

Six doors, one contract

4 / 9 · the volume

FUSE is one of six ways into a volume, and every one of them is authorised by Unity Catalog grants on the volume. The FUSE door is the narrowest: it writes whole files front to back and refuses the rest — and Databricks documents the refusals, the reason for them, and the way round.

flint on Kubernetes

5 / 9 · passthrough and lean

flint cannot own the machine, so it uses the hook Kubernetes gives a storage system: a CSI node plugin that kubelet calls before a pod's containers start. Passthrough and lean share the plugin, the worker namespace and the broker, and differ in one thing — whether the pod gets a FUSE mount or a plain local directory. Both run against any S3-compatible store, in any cluster, on-premises included.

Where a write lands

6 / 9 · the write path

Databricks /Volumes and flint passthrough make the same promise, because both are FUSE over whole objects: a file becomes an object when it is closed, and anything that needs to edit an object in place is refused. flint lean makes a different promise: a write is visible at once on local disk and durable at the next boundary, and nothing is refused.

The other two front ends. flint lite (an NFS hub per share) is the answer when two pods must see one live tree, with byte-range locks — the shape Databricks reaches for when its KB tells a customer to ask for an NFS mount. flint forge (git over S3) has no Databricks counterpart.

What carries over

8 / 9 · lessons

The part of Databricks worth copying is not its FUSE daemon, which by every public sign is a goofys descendant with goofys' limits. It is everything around the mount: identity from the platform, grants and short-lived credentials from one authority, a small contract written down, and other doors to the same bytes. flint already has most of that in Kubernetes form. The one thing that does not carry over is the shared mount.
