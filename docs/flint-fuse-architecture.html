Flint-fuse — no hub, one bucket

1 / 5 · architecture

The proposal: no hub. A webhook-injected sidecar runs the same tier engine behind a FUSE mount; agents and the project service reach S3 directly; the bucket format — whole-file objects, .flint/ control cells, guarded publishes — is unchanged, so hub-mode and direct-mode volumes stay mutually convertible. Reviewed adversarially against the code on 2026-08-24 (14 agents, 7 dimensions); the corrections are folded into these pages.

The operator becomes a webhook

2 / 5 · control plane

One CR still governs a share, but in direct mode it renders no standing objects — the operator's job becomes admission: allocate non-overlapping subtree prefixes, stamp the claim identity, inject the sidecar into matched pods, and detect the pods that slipped past.

The tier engine moves into the pod

3 / 5 · data path

src/tier — capture, durable, gate, flush, evict, hydrate, epoch, manifest, import — ports into the sidecar unchanged; the FUSE front reproduces the NFS front's hook discipline. What does not port is the coherence inversion: reading other writers' work while serving, under leases scoped to subtrees.

The failure-shape trade

4 / 5 · failure model

The honest headline is not “no single point of failure.” Hub mode concentrates failure into rare, share-wide, hang-shaped outages; direct mode distributes it into frequent, per-pod, loss-shaped events. The full matrix — including the two rows the proposal creates and the two it deletes.
