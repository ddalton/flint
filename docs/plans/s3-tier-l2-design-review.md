# S3 Cold Tier (L2) — the ultracode design review and the reshaped design

**Date:** 2026-08-15 · **Verdict: RESHAPE** (then proceed in the revised order below)
**Provenance:** 15-agent adversarial review (5 code-grounded lenses → 6-finding
adversarial verification → 2 independent economics models → judge → synthesis),
run before any implementation. 34 findings raised; the top 6 (all rated
critical) were adversarially verified and **all 6 were CONFIRMED, none
refuted**. Economics gate: **CONDITIONAL GO** — the five knobs it names are
promoted to design requirements (A11).

This document supersedes the v1 design sketch. Implementation follows the
order at the bottom; each amendment cites the codebase precedent it builds on.

## The verdict, in one paragraph

The design's core mechanism (dirty intervals → multipart generation assembly → whole-file objects → evict-to-marker/hydrate) survives review, but its central safety claim — "pessimal upload, never wrong data" — is falsified in at least four independent, adversarially-CONFIRMED ways in normal operation: (1) the capture surface misses six byte-mutating lanes (SETATTR-size, OPEN-createattrs size, ALLOCATE, DEALLOCATE, COPY, CLONE), so UploadPartCopy stitches stale bytes into generations that then self-certify via ETag and destroy data through evict/hydrate — the exact disease of the ftruncate bug just fixed in v1.25.2, re-shipped one layer up; (2) in the full-pNFS posture the flusher as placed reads the sparse size-only MDS stub, uploads verified zeros, and eviction deletes the only real copy — F67 with the survivable property engineered away; (3) dirty knowledge has no durable anchor, so after any routine spot-reclaim restart the persisted "clean at gen g" rows either destroy committed post-g writes at eviction or force whole-resident-set re-uploads; (4) no per-file exclusion primitive exists anywhere in the tree, so generations are never point-in-time images and eviction races in-flight lock-free pwrites. Add the confirmed evict/hydrate interactions with the F17b/c fd-cache (renamed-restore splits every open fd; WRITE-to-evicted .create(true)s zeros over real data) and the path-keyed rows colliding with git's rename-over idiom, and the design is missing whole sections — recovery, concurrency, namespace mutation, observability — not just guards. The verdict is reshape, not halt: every confirmed finding has a concrete fix with an existing codebase precedent (truncate_pending durable gate, stub_binding xattr-before-record, note_rename identity re-keying, NFS4ERR_DELAY parking, evict_path), the economics gate is a conditional GO whose five knobs fold directly into the amendments, and the flint-lite scope cut the user already made on 2026-08-15 eliminates the worst critical outright. Revise the design per the amendments below, then implement in the order given, which proves the local correctness machinery (capture, durability, exclusion) before any byte reaches a bucket and defers the destructive operations (eviction) until the guards they depend on are drill-proven.

## The six confirmed findings

### C1 (critical, crash-restart) — No durable per-file dirty record: after any restart the 'whole file dirty' fallback is unanchorable, and stale clean generation rows make eviction destroy un-flushed writes

**Claim:** The design keeps the dirty interval log in process memory with 'flush-level' durability and claims a lost log safely degrades to 'whole file dirty' — but nothing in the state backend can tell the server WHICH files were dirtied since their last flush, or even that the log was lost rather than empty. The generation row (gen g, ETag, flush state 'clean') survives the crash while the knowledge that the file was re-dirtied does not, so after restart every row that says 'clean, durable at gen g' is untrustworthy.

**Fix:** Add a durable per-file dirty BIT (not the intervals) in the same sqlite backend the MDS already opens with synchronous=FULL (/Users/ddalton/github/flint/spdk-csi-driver/src/pnfs/config.rs:736-746 — the group-commit writer amortizes exactly this kind of small transaction). Set it transactionally on the FIRST dirtying write of each flush cycle, before any stable-WRITE ack or COMMIT return for that file; clear it in the same transaction that commits generation g+1. Intervals stay in memory: a crash then degrades to whole-file upload for exactly the bit-set files — the design's claimed fallback, made real. Eviction requires bit clear. In the full posture the bit must live in the MDS backend and be set at RW-LAYOUTGET grant time (the MDS's only guaranteed observation point for DS-lane writes), cleared only after a flush that the DS's interval log survived.

**Verification:** CONFIRMED, not refuted. I re-derived the mechanism from the code and the design text.

EVIDENCE CHAIN — every citation checked out:
(1) Writes leave no durable trace outside the data file: /Users/ddalton/github/flint/spdk-csi-driver/src/nfs/v4/operations/ioops.rs:1426-1435 (UNSTABLE4 = no sync; FILE_SYNC4/DATA_SYNC4 = sync_all/sync_data on the file only) and 1539-1554 (COMMIT = sync_all on a cached or fresh fd, nothing else). Neither path touches the state backend.
(2) Startup cannot distinguish crash from clean start and restores no dirty knowledge: /Users/ddalton/github/flint/spdk-csi-driver/src/pnfs/mds/server.rs:421-523 (load_persisted_state loads clients/sessions/stateids/layouts/placements/geometry — no cleanliness marker); /Users/ddalton/github/flint/spdk-csi-driver/src/state_backend/sqlite.rs:1093-1108 (increment_instance_counter bumps unconditionally). The full schema (sqlite.rs:1988-2444) has no per-file dirty/flush table.
(3) A routine pod stop IS a log loss: /Users/ddalton/github/flint/spdk-csi-driver/src/nfs_mds_main.rs has zero signal handling (grep for tokio::signal/unix::signal: 0 hits), and flint-lite runs exactly this binary (/Users/ddalton/github/flint/flint-csi-driver-chart/templates/lite.yaml:144 — command: ["/usr/local/bin/flint-pnfs-mds"]). On this project's pure-spot posture, MDS restarts are routine.
(4) Full posture is worse: /Users/ddalton/github/flint/spdk-csi-driver/src/nfs_ds_main.rs (132 lines) constructs no state backend at all — a DS death loses its half of the interval log while the hub's log looks intact, so even a hub-side restart-fallback misses it.
(5) mtime is not a substitute: /Users/ddalton/github/flint/spdk-csi-driver/src/nfs/v4/operations/fileops.rs:541-558 — SETATTR applies client-supplied mtime via File::set_times (futimens), so a "file mtime newer than flush mtime" check is spoofable/defeatable.
(6) The proposed fix is feasible in existing machinery: /Users/ddalton/github/flint/spdk-csi-driver/src/pnfs/config.rs:736-763 — the MDS opens sqlite with open_durable (synchronous=FULL) and a group-commit writer that exists precisely to amortize small per-op transactions.

DESIGN RE-DERIVATION: §2 makes dirty-capture durability "flush-level only" and claims a lost log "falls back to whole file dirty". After ANY restart the in-memory log is empty; with no durable per-file bit and no clean-shutdown marker, that fallback is unanchorable exactly as claimed — its scope is either (a) nothing (trust the persisted rows) or (b) every resident file on every restart including graceful ones. Path (a) is the data-loss path: UNSTABLE write + COMMIT acked (sync_all succeeded) → spot reclaim → restart → the §4 row still reads "clean at gen g, ETag e" → §5's eviction gate verifies the S3 OBJECT against the RECORDED ETag (the anti-foreign-overwrite relation), never the local file against the S3 object — the stale-clean row passes, truncate-to-marker destroys the committed post-g writes, and later hydration serves gen g with a MATCHING If-Match, so even the design's 412 tripwire stays silent. Note the multipart ETag is not a content MD5, so the gate as specified cannot verify local content even in principle. Path (b) is not the design's advertised occasional "pessimal upload": with no cleanliness marker it is a whole-resident-set re-upload per routine pod reschedule with eviction (capacity relief) blocked until it completes, and it still misses the DS-death case, whose log loss happens without any hub restart. The design has no startup/recovery section at all, and its persisted "flush state" column is precisely what a straightforward implementation would trust — a persisted clean that outlives its truth.

DECISIVE CODEBASE PRECEDENT: the repo already solved this exact hazard class for the block tier with a durable per-file gate — sqlite.rs:2076-2087, file_placement.truncate_pending, commented "persisted so a restart during a parked truncate does not come back ungated", restored at startup via resume_parked_truncates (server.rs:482). The S3 design's dirty knowledge gates eviction the same way the truncate gate gates layouts, yet is specified memory-only. The proposed durable dirty bit is this repo's own established discipline, omitted.

Nothing in the finding rests on an uncertain S3 API behavior. Severity critical is defensible: the data-loss branch is reachable in completely normal operation (COMMIT-acked write, routine spot reclaim, capacity-driven eviction) under the design's most natural reading, and the only safe alternative reading is an unstated full-re-upload-per-restart regime that the design neither specifies nor costs.

### C2 (critical, crash-restart) — Eviction's truncate-to-marker order is unpinned: truncate-before-marker crash reproduces the F67 silent-zeros shape and then uploads the empty stub over the good S3 object

**Claim:** §5 gates eviction on a confirmed durable S3 generation but never pins the order of the two non-atomic local steps: committing the marker (xattr + MDS row) and truncating the file. If the truncate lands first and the hub dies before the marker commits, the file is a plain 0-byte file with no marker — indistinguishable from a genuinely empty file to every existing code path.

**Fix:** Pin the order in the design text and enforce it in code: (1) durably commit the eviction row AND write the stub xattr; (2) only then truncate — mirroring stub_binding's existing xattr-before-record discipline. Make READ/OPEN consult eviction state before trusting local size (the §6 MDS-path-serve hook must sit ahead of ioops.rs:1171's size check). Add a startup reconciler pass: marker present + local length > 0 → finish the truncate (or clear the marker); and make 'marker set' unconditionally exclude a file from flush — never upload bytes from a file whose eviction marker is set.

**Verification:** CONFIRMED, re-derived independently. (1) Code claim verified: spdk-csi-driver/src/nfs/v4/operations/ioops.rs:1172-1185 — MDS-lane READ takes file.metadata().len() and returns Nfs4Status::Ok/eof=true/empty data whenever offset >= file_size; no xattr, MDS row, or backend state is consulted anywhere on the read path, and server.rs:209-218 confirms standalone (lite) routes EVERY read through this lane. A post-truncate/pre-marker crash therefore leaves a 0-byte file indistinguishable from a genuinely empty one to every existing code path. (2) Precedent claim verified: stub_binding.rs:1-13 documents the F67 silent-zeros incident and the learned rule (xattr written BEFORE the backend record, same failure domain); server.rs:147-183 boot-refuses the equivalent divergence configuration. Sharpening nuance: server.rs:154-162 permits xattr-LESS export filesystems in standalone mode, so the §5 marker's xattr half may not even be writable on a bootable lite deployment. (3) Design claim verified: §5 pins only durability-before-capacity-return; the relative order of marker commit (xattr + sqlite row — themselves non-atomic across two failure domains) vs truncate is unspecified, and no startup reconciler exists in §1-§10. (4) Consequence chain verified: §6's hydration/no-layout hooks key off the marker that was never committed, so the stub serves as empty (immediate application-level corruption). Then §2's stated crash fallback ('lost log = whole file dirty') plus the truncate-modified mtime makes the stub eligible for the next flush; the §4 row records generation/ETag/flush-state but not size, so nothing detects the divergence. The S3 guard cannot save it: x-amz-copy-source-if-match / conditional PUT compare against gen g's ETag, which STILL MATCHES (no foreign overwrite occurred) — the guard detects foreign writes, not a corrupted local source — so the 0-byte file publishes as gen g+1 via plain PUT (below any multipart threshold), destroying the only durable copy. This also falsifies §2's 'never wrong data' claim for the fallback. Refutation attempts all failed: 'implementation would order it correctly' is refuted by this repo's own F67 history of shipping exactly this mistake when unpinned; 'the ETag guard catches it' is refuted by the guard's condition being satisfied; 'READ consults eviction state' is refuted by ioops.rs:1144-1195. The proposed fix (marker-durable-before-truncate, READ consults eviction state ahead of the size check, startup reconciler, marker excludes file from flush) is necessary and mirrors the existing stub_binding discipline. Severity note: the trigger requires a crash mid-eviction (a routine background operation on spot-heavy deployments), and the delayed consequence is permanent loss of the only durable copy — critical is defensible; at minimum high under the rubric's crash clause.

### C3 (critical, concurrency-coherence) — No per-file exclusion primitive: a 'generation' is never a point-in-time image, and eviction's only stated guard (verified ETag) cannot establish local==S3

**Claim:** The design's flush reads local bytes while writes land, and its eviction gate is solely 'confirmed durable S3 generation' (design point 5). Nothing in the design or the codebase can atomically establish 'no bytes changed since flush start and none are in flight': the MDS write lane is deliberately lock-free positioned pwrite on shared fds from untracked spawn_blocking tasks, the DS lane likewise, and there is no per-file gate anywhere in the NFS tree. Eviction racing one in-flight UNSTABLE write loses that write permanently; a READ racing the marker swap serves marker bytes/zeros. Long-open files (sqlite DBs, git index — the exact workloads drill-proven by commit 934ae78) never pass through a closed/quiescent state, so either they never flush/evict (unbounded local-capacity pin, defeating the tier) or their published generations are perpetually torn — and design point 8's disaster recovery is rebuild-from-bucket, which would restore a torn sqlite image as if it were data.

**Fix:** Add the missing primitive to the design before implementation: a per-file write-gate in the shared dirty-capture module — entry/exit counters around every byte-mutating syscall in both lanes, plus an 'evicting/hydrating' flag checked before pwrite. Eviction requires: gate drained + dirty log empty (epoch-swapped atomically with drain) + no writable open stateids and no lock-holding opens (state_mgr enumeration) + fd-cache residuals for the path evicted. Define generation semantics honestly: a generation is fuzzy unless produced under the gate; only gated generations are eviction-eligible; open-hot files are declared non-evictable and their objects labeled fuzzy (metadata flag) so bucket readers and DR know.

**Verification:** Independently confirmed the mechanism from the code. (1) Both write lanes are deliberately lock-free positioned writes on shared Arc<File> fds: ioops.rs:1417-1424 ("pwrite… No mutex needed; the kernel serializes at the page-cache level" — finding cited 1401-1408, actual 1417-1424, content verbatim) and ds/io.rs:68-80 + 527-533 ("safe to issue concurrently on the shared cached fd"). (2) No per-file exclusion primitive exists anywhere in src/nfs or src/pnfs — the only drain gate is the F55 server-wide shutdown DrainGate (pipeline.rs:62-107, connection-level, global); everything else is wire-serialization mutexes. (3) Quiescence is not even decidable from state: seed_open_fd shares one Arc<File> across stateids (ioops.rs:322-331), residual fds of dead clients outlive state entries (ioops.rs:310-311, exact), and handle_write explicitly admits the ANONYMOUS_STATEID (ioops.rs:1254-1267), so enumerating writable open stateids cannot see all writers. (4) No invalidation can fence in-flight I/O: FdCache's F24 design hands out owned Arc<File> clones ("no guard escapes"), removal is by-stateid only — no MDS-side evict-by-path exists (only the DS has evict_path, ds/io.rs:73-80) — and a write task already holding its clone pwrites after any purge; worse, WRITE's open path uses .create(true) (ioops.rs:1322-1327), so a post-eviction write silently recreates the marker path. (5) Lock records are fh-keyed pure state with no fd (lockops.rs:96-114; cited line 106 is the filehandle field), untouched by eviction. Design-side: point 5's sole gate (verified ETag) is a durability check, not an exclusion primitive; point 6 fences only NEW layout grants (no recall of outstanding layouts); the quarantine-sweep discipline is capacity-return ordering, not write fencing. The dirty-interval log does make flush-tearing self-healing LOCALLY (racing writes re-logged, re-uploaded next generation), so I probed that as a refutation — but it fails at exactly the finding's two sinks: eviction destroys local authority (even a charitable evict-requires-empty-log check leaves an unclosable TOCTOU because nothing makes check+marker-swap atomic against the lock-free lanes; hydration's If-Match GET then restores the recorded generation and the racing write vanishes), and point 8's rebuild-from-bucket promotes fuzzy generations to authoritative (sqlite db and -wal are separate objects flushed at independent barriers — states no crash could produce, presented as successful recovery). One consequence leg is overstated: READ-racing-eviction serving zeros (b) is contingent on a truncate-in-place marker — an unlink-and-replace marker with the F17c anchored fds (ioops.rs:302-311) would serve old-but-consistent bytes — but the design leaves marker mechanics unspecified, and legs (a) lost-write-at-eviction and (c) torn-DR stand independently. The claimed critical severity is defensible: (a) is reachable in normal operation for any eviction policy the design as written permits, and forbidding eviction of open-hot files without the missing primitive yields the unbounded local-capacity pin the finding also names.

### C4 (critical, concurrency-coherence) — Full-pNFS mode: the MDS file for a tiered striped file is a sparse size-only stub — a naively-placed flusher uploads zeros, verifies their ETag, and eviction then destroys the only real copy

**Claim:** Design point 2 hooks the DS write lane, so full-pNFS tiering is in scope, but the design never says WHERE flush reads bytes or where hydration writes them. In full mode a striped file's bytes live only on a DS at a rebased path; the MDS-local file is explicitly a sparse size-only stub, and even MDS-fallback I/O is proxied to the DSes (F66) rather than served from local bytes. A flusher running beside the generation rows (MDS state backend, design point 9) reads the stub → uploads a zero-filled object → the ETag verification in the eviction gate confirms durable ZEROS → eviction deletes the DS stripe file. Additionally, 'ONE shared module' shares code, not state: DS-lane dirty intervals accrue in the DS process on another node, while flush state and generation rows live in the MDS sqlite — the cross-process log/flush coordination protocol is entirely unspecified.

**Fix:** Pick one explicitly in the design: (a) v1 scopes flush/hydration/eviction to bytes the MDS process itself hosts — lite mode plus never-layouted files — gated by the same predicate refuse_if_striped already uses (pnfs.is_pnfs_managed, dispatcher.rs:2277), with tiering refused for placement-pinned files; or (b) specify a DS-resident flush/hydration agent plus an MDS-orchestrated protocol (interval-log shipping, generation-row ownership, which process holds S3 credentials, what happens when the DS dies mid-multipart). Option (a) matches the flint-lite reframing of 2026-08-15 and removes a whole class of cross-process races from v1.

**Verification:** CONFIRMED — every code citation verifies and the codebase itself treats the finding's mechanism as its canonical corruption shape. (1) dispatcher.rs:2280-2284 says verbatim that a striped file's MDS-local file is "a sparse size-only stub... data that is not here"; stub_io_disposition (2287-2358) never serves striped bytes locally (Delay/FailFast/Proxy only), and the F66 proxy write (1520-1551) sends bytes to the DS and only set_lens the stub. (2) ds/io.rs:664-703 confirms the bytes live at a DS-rebased path in another process/node, and operations/mod.rs:1329-1373 (proxy_fallback_read_impl) shows the ONLY way the MDS process reaches real striped bytes is gRPC ReadStripe to DS endpoints — a protocol the design never mentions for flush or hydration. (3) The codebase carries three independent guards against exactly the read a naively-placed flusher would perform: F67 boot refusal (server.rs:147-183, "restart = silent zeros"), the scsi-class FailFast (operations/mod.rs:229-247, "would serve the stub's zeros for committed data — F67's exact shape"), and the sparse-stub-no-binding refusal (mod.rs:273-294, "serving zeros is silent corruption"). The design adds a fourth reader of the stub with no such guard. (4) Full-pNFS is in scope as written: point 2 hooks the DS write lane and point 6 specifies full-mode layout denial; the lite-only scoping is the finding's proposed fix (a), not present in the design (docs/flint-lite.md mentions the S3 tier but no such scope). (5) stripeWidth=1 does not rescue it: layout.rs:1639-1646 shows width only narrows the DS pin — a width-1 file is still DS-resident and pnfs-managed. (6) The eviction gate is content-blind: S3 ETag/If-Match attests the uploaded object's identity, not fidelity to the DS stripes, so a zero-filled upload passes "verified ETag" and eviction then removes the only real copy (capacity return in full mode necessarily means deleting DS stripe bytes). Hydration's "restores the local file" is equally unplaced — restored MDS-local bytes are invisible to the layout path that still treats the file as a stub. Minor caveat: the sub-claim about DS-side interval logs, taken alone, only degrades to the design's own "whole file dirty" pessimal fallback rather than corruption — but it is accurately characterized as an unspecified cross-process protocol, and the primary byte-source/eviction/hydration gap it compounds is fully confirmed. Severity critical is warranted: in full mode with tiering enabled, first flush + eviction of any striped file destroys the sole copy in normal operation with the safety gate reporting success.

### C5 (critical, concurrency-coherence) — Dirty capture hooks only the two WRITE lanes, but five other ops mutate file bytes: DEALLOCATE, SETATTR-size, OPEN(size), COPY, CLONE — flush then publishes 'never wrong data' that is wrong

**Claim:** Design point 2 names exactly two hook points (ioops.rs handle_write, DS write path). The MDS lane mutates file bytes in at least five other places that would leave the interval log clean while changing content: DEALLOCATE punches real holes, SETATTR truncates via set_len, OPEN applies a createattrs size (O_TRUNC — the most common write-open pattern that exists), and server-side COPY and CLONE write destination bytes wholesale. For any such range the flush's UploadPartCopy sees 'untouched since gen g' and stitches the OLD bytes into generation g+1 with a passing If-Match guard. The design's safety fallback ('a lost log falls back to whole-file dirty') does not cover a log that is present but incomplete — the failure is silent by construction.

**Fix:** Respecify the capture surface as 'every code path that mutates file content or size', enumerated against the codebase: handle_write, DS write, handle_allocate/deallocate, handle_copy, handle_clone, SETATTR-size, OPEN-createattrs-size, and the F66 proxied-write arm. Truncations must be first-class log events (a shrink invalidates all parts beyond the new EOF and forbids UploadPartCopy of them; a shrink-regrow marks the intervening range dirty). Add a debug-build assertion in the shared module: file mtime/change-counter advanced (change_counter is already bumped in these paths) with no corresponding log entry → panic in tests, loud metric in prod.

**Verification:** CONFIRMED — I re-derived each claimed bypass from the code and each one mutates file bytes/size outside the design's two named hook points (ioops.rs handle_write, DS write path):

1. DEALLOCATE: spdk-csi-driver/src/nfs/v4/operations/perfops.rs:1103-1125 routes to fallocate_current_fh (perfops.rs:1010-1097), which does a real fallocate(FALLOC_FL_PUNCH_HOLE|FALLOC_FL_KEEP_SIZE) on the backing file and bumps the change counter (1078). KEEP_SIZE means size is unchanged and the punched range now reads as zeros — the exact shape where a clean interval log makes flush UploadPartCopy the pre-punch bytes. The F15 comment (perfops.rs:1118-1120) documents that this handler deliberately punches REAL holes.
2. ALLOCATE: perfops.rs:985-1004, real fallocate mode 0 (extends size), same bypass.
3. SETATTR size: fileops.rs:518-531 — OpenOptions.write(true).open(path).set_len(size); a truncate or extend with no per-range record anywhere.
4. OPEN with size createattr: ioops.rs:582-601 — on an EXISTING file, `SettableAttrs { size: want.size, .. }` is applied via apply_settable_attrs_offloaded, i.e. O_TRUNC semantics before any WRITE RPC exists. The comment at ioops.rs:562-565 confirms this is the intended truncate-at-open path.
5. COPY: perfops.rs:518-729 resolves both ends from stateids and writes destination bytes with write_at (perfops.rs:700-703), sync_all + bump_change_counter (719, 726) — never enters handle_write. Linux NFSv4.2 clients map copy_file_range to COPY, so this fires in normal operation.
6. CLONE: perfops.rs:884-938 reflinks (try_reflink_range) or copy_range's the destination range, bump_change_counter (923, 932).

Guard coverage check (the one plausible refutation): COPY/CLONE refuse only is_striped ends (perfops.rs:609-623, 858-869), and ALLOCATE/DEALLOCATE/SEEK are refused only for striped files at dispatcher.rs:1679-1698 via refuse_if_striped; the dispatcher test at dispatcher.rs:4525 confirms a dispatcher with no pnfs handler returns None (serves them). In flint-lite/standalone there is no pnfs handler, so every one of these ops runs against the real exported file — and lite is a first-class posture of this design (point 1: "Lite: files live in the MDS export tree directly"). Even in full-MDS mode, never-layouted files are deliberately kept fully writable MDS-path (perfops.rs:495-500), and design point 6 makes evicted-then-hydrated files MDS-path served, so the bypass is reachable there too.

S3 side: UploadPartCopy's x-amz-copy-source-if-match is evaluated against the SOURCE object (gen g). Local mutations never change gen g's object or ETag, so the guard passes by construction — it detects foreign bucket overwrite only, and structurally cannot detect a locally-stale part. A part covering a punched hole (or a shrink-regrow gap) is "untouched since gen g" in the log, gets server-side copied, and CompleteMultipartUpload publishes g+1 containing bytes the application destroyed. The design's only safety fallback ("a LOST log falls back to whole-file dirty") addresses log absence, not a present-but-incomplete log; the failure is silent, no crash required. One caveat that does not save the design: a pure shrink alone can come out correct if flush derives object length from local file size, and an O_TRUNC-then-full-rewrite is masked by the rewrite's captured intervals — but DEALLOCATE (hole punch, size unchanged) and shrink-then-regrow corrupt g+1 unconditionally, and hydration/rebuild-from-bucket then serves the resurrected bytes back. Severity critical stands: data corruption in normal operation for hole-punching workloads (VM images via qemu/virtiofs, torrent clients, fallocate --punch-hole), violating the design's own "never wrong data" invariant. The proposed fix direction (enumerate every content/size-mutating path; the change-counter bumps already present in each path are a ready-made cross-check hook) is consistent with what the code shows.

### C6 (critical, concurrency-coherence) — Hydration vs the path-keyed fd-cache: restore-by-rename splits every open fd from the file; restore-in-place exposes torn reads; and a bare WRITE to an evicted file .create(true)s an empty file whose part-rounded flush uploads zeros over real data

**Claim:** The design says hydration 'restores the local file, then serves' (point 6) without specifying the restore mechanism, and every naive mechanism corrupts against this codebase. (a) tmp+rename restore: OPEN of the evicted file has already seeded an fd of the MARKER inode; READ/WRITE cache hits filter by PATH equality, not inode, so after the rename the stateid's fd still matches (same path, dead inode) — READs serve marker bytes/EOF, WRITEs land in the unlinked inode and evaporate; the F17b/by-ino fallbacks are explicitly engineered to keep routing I/O to the old inode. The MDS FdCache has no evict-by-path API at all (the DS grew evict_path for exactly this unlinked-fd failure; the MDS cache never did). (b) In-place restore: handle_read serves whatever is on disk with eof computed from current size, so a concurrent READ mid-restore returns a short read with eof=true that the kernel client caches as the file's end. (c) Independent of restore choice: handle_write's cache-miss path opens with .create(true), so a WRITE to an evicted file silently materializes an empty file; with intervals 'rounded to S3 part boundaries' (design point 2), flush uploads the whole enclosing part from local bytes — bytes the local file never had (they exist only in S3) upload as zeros into g+1.

**Fix:** Specify in the design: hydration restores IN-PLACE into the marker inode (open the existing file, ftruncate, pwrite object bytes, fsync) so every cached fd stays valid; hydration and eviction are single-flight per file and hold the same per-file gate as finding 1, with READ/WRITE/OPEN parking (NFS4ERR_DELAY, the exact precedent stub_io_disposition uses at dispatcher.rs:2331-2336) until restore completes; WRITE to an evicted file triggers hydration-before-write as a barrier (never .create-and-write); and add an evict-by-path API to the MDS FdCache mirroring DS evict_path for the eviction path's use.

**Verification:** Independently re-derived all three limbs from the code. (a) tmp+rename restore: OPEN seeds a marker-inode fd (ioops.rs:867-870 → seed_open_fd at 312-351, fresh-opens the path); READ/WRITE cache hits filter by path equality only with no on-disk inode revalidation (ioops.rs:1126-1135, 1302-1311); v3 filehandles are inode-pinned (filehandle.rs:409-434), so after rename-over the resolve goes STALE and stale_open_fallback (ioops.rs:358-384) deliberately routes I/O to the ORIGINAL (marker, now unlinked) inode by embedded path/ino — v4 kernel handles reach the same fallback via ESTALE (filehandle.rs:378-395). Both resolution outcomes therefore pin the stateid's I/O to the dead marker inode: stale reads, silently lost writes. The MDS FdCache (fd_cache.rs, read in full) has only remove-by-stateid — no evict-by-path/ino API — while the DS grew evict_path (pnfs/ds/io.rs:345-349) for exactly the out-of-band-unlink failure (rationale at io.rs:73-80). (b) In-place restore: handle_read computes eof from the file's size at read instant (ioops.rs:1172-1194), so a concurrent READ mid-restore returns a short read with eof=true; the only hydration code in the tree is a TEST-ONLY env-gated sleep (ioops.rs:1103-1117, 1587-1609), READ-only, no coherence gate. (c) WRITE cache-miss opens .create(true) (ioops.rs:1322-1327); design point 6 hydrates on READ only, with no WRITE barrier; S3 multipart parts upload whole (sub-range patching impossible; UploadPartCopy only copies from an existing object, reserved by the design for untouched parts), so the enclosing dirty part of a written-while-evicted file uploads local sparse zeros over gen-g data into g+1. The fix's NFS4ERR_DELAY parking precedent verified at dispatcher.rs:1415-1419/1498-1502/2290-2336 (stub_io_disposition, 'local file is a sparse stub'). Cited line numbers are offset ~15-25 lines from the current tree but name the correct mechanisms throughout. Severity critical stands: the READ that triggers hydration itself carries an OPEN whose marker fd is already seeded, so hydration-under-open is the steady state; corruption/loss is reachable in normal operation. No refutation angle survived: the F17b/c machinery makes rename-restore corrupt by design, the code has no gate for in-place restore, and the design text specifies no WRITE barrier.

## The amendments (the reshaped design)

A1 — Scope v1 to flint-lite plus never-layouted files, full stop. Tiering is refused for any is_pnfs_managed file (the exact refuse_if_striped predicate, dispatcher.rs:2277); the DS write-lane hook, DS-resident flusher, and cross-process interval-log protocol are cut from v1 and deferred to a separate design. This kills the confirmed critical where the flusher reads the sparse MDS stub, uploads verified zeros, and eviction deletes the only real copy — and it matches the 2026-08-15 flint-lite reframing.

A2 — Respecify dirty capture as mutation-complete, enumerated from the dispatcher, not the write lanes: one note_content_mutation(file, range|whole) called from every site that bumps the change counter on a regular file — handle_write, SETATTR-size (fileops.rs:525), OPEN-createattrs size (ioops.rs:582-601), ALLOCATE, DEALLOCATE (perfops.rs:1010-1125), COPY (perfops.rs:518-729), CLONE (perfops.rs:884-938). Truncation is a first-class log event (shrink invalidates all parts past new EOF and forbids their UploadPartCopy; shrink-regrow marks the gap dirty; DEALLOCATE marks the range dirty-as-zeros). Stated module invariant: unknown mutation ⇒ whole-file dirty. Debug assertion: change-counter advanced with no log entry ⇒ panic in tests, loud metric in prod.

A3 — Add a durable per-file dirty BIT (not intervals) in the MDS sqlite synchronous=FULL lane, following the repo's own truncate_pending precedent (sqlite.rs:2076-2087): set transactionally on the first dirtying mutation of each flush cycle before any stable-WRITE ack or COMMIT return; cleared in the same transaction that commits generation g+1. Intervals stay in memory; a crash degrades to whole-file upload for exactly the bit-set files — the design's claimed fallback, made real. Eviction requires bit clear. Persist the interval log incrementally (periodic append) so a crash costs minutes of dirtiness, not the whole open-for-write set (defuses the re-upload storm into the 3,500-RPS prefix).

A4 — Add the missing per-file exclusion primitive to the shared tier module: entry/exit counters around every byte-mutating syscall plus an evicting/hydrating flag checked before pwrite, with per-file flush single-flight. Eviction requires: gate drained + dirty log empty (epoch-swapped atomically with the drain) + no writable open stateids, delegations, or byte-range locks + fd-cache entries for the file purged (by path AND by ino — the ANONYMOUS_STATEID and dead-client residual fds mean open-state enumeration alone is not sufficient). Only gate-produced generations are eviction-eligible; open-hot files are declared non-evictable. This doubles as the economics gate's mandatory quiescence knob.

A5 — Pin the eviction/hydration state machine. Eviction: durably commit the eviction row AND stub xattr FIRST, truncate second (stub_binding's xattr-before-record discipline); READ/OPEN must consult the marker before trusting local size (ahead of ioops.rs:1171's size check); marker set ⇒ file unconditionally excluded from flush; startup reconciler finishes or rolls back half-evictions. Hydration: restore IN-PLACE into the marker inode (open, ftruncate, pwrite, fsync — never temp+rename, which splits every F17b/c cached fd and goes STALE on inode-pinned v3/v4 handles); single-flight per file behind the A4 gate; concurrent READ/WRITE/OPEN park on NFS4ERR_DELAY (the stub_io_disposition precedent) with the in-RPC hold bounded well below timeo (15-30s) and the fetch continuing in background off the pipeline permit; WRITE and size-SETATTR to an evicted file are hydrate-first — the .create(true) path must never materialize an empty file under a marker. Add evict-by-path/ino to the MDS FdCache mirroring the DS's evict_path. Note: with DELAY-based hydration, open gate (b) becomes a DELAY-retry-behavior measurement, not a raw READ-hold measurement — re-scope the rig test accordingly.

A6 — Guard every publish and split the 412 posture. All updates carry If-Match on gen g's ETag on BOTH PutObject and CompleteMultipartUpload (GA since 2024-11); new keys carry If-None-Match:* (also closes the create race with outside writers). A durable flush-intent row {path, from_gen, to_gen, flush_uuid, mpu_id, base_etag} commits before CreateMultipartUpload/PUT, and every publish is stamped x-amz-meta-flint-{gen,epoch,flush_uuid} plus a full-object checksum (CRC64NVME — works across multipart; the multipart ETag is NOT a content hash and must never be treated as one). 412/409 arbitration is always by HEAD: own stamp at g+1 ⇒ torn own flush, adopt the object; ETag == base_etag ⇒ Complete never landed, abort and re-flush; anything else ⇒ genuinely foreign. Posture split: copy/publish 412s are internal fencing events (abort + re-flush from local truth — LOCAL wins); only hydration-GET 412s are foreign-overwrite (S3-wins). A bare 412 must never route to operator re-ingest — as written, the design's own crash window converts the safety runbook into a data-loss procedure.

A7 — Key generation/eviction rows by file identity (the F67 file_id binding), with the S3 object key as a mutable attribute; hook note_rename/note_remove (already called from the dispatcher for exactly this purpose) to re-key rows and schedule a guarded server-side bucket re-key at the next flush barrier; hydration honors the stored key in the interim. REMOVE writes a tombstone consumed by flush (delete object) and respected by import-refresh (never re-ingest a tombstoned key until flushed) — otherwise every import resurrects deleted/renamed-away files. Rename-over tombstones the covered file's generation atomically. LINK on tiered volumes is refused in v1 (dispatcher.rs:1968 precedent). Without this, git's tmp-write+rename idiom — the tier's proof workload — produces false foreign-overwrite wedges on every object finalize.

A8 — Specify the epoch object: holder = persisted server_id (sqlite.rs:1123) + lease deadline, renewed by periodic If-Match CAS re-PUT; a restarted hub whose server_id matches resumes immediately (self-recognition — without this, every routine spot reclaim wedges the mount behind a manual CAS); a successor claims only after N missed heartbeats judged against S3's own Last-Modified clock; an incumbent that fails its own renewal self-fences (stops serving, aborts flushes); every flush re-verifies the epoch before publish. At claim, the successor MUST ListMultipartUploads under the volume prefix and abort all — fencing every deposed-hub Complete with NoSuchUpload. Document the residual window: a deposed hub's plain PUT is fenced only by the heartbeat interval plus the A6 If-Match guard. Specify the client-address migration story for handoff (Service/LB follows the epoch holder) or document handoff = fleet remount — runbr proved clients pinned to a dead address just hang.

A9 — Bucket bootstrap and MPU hygiene as hub-start requirements, not operator advice: verify/create the AbortIncompleteMultipartUpload lifecycle rule (1-7 days); AbortMultipartUpload on every terminal failure path including the 412 loud-fail; startup sweep aborts every MPU with no live intent row; GetBucketVersioning and enforce the declared posture (recommend Versioning ON + NoncurrentVersionExpiration as the explicit recovery window, with the noncurrent tail priced into economics — refuse or loudly degrade on the untested configuration); document the IAM surface (s3:ListBucketMultipartUploads, s3:AbortMultipartUpload, kms:Decrypt for UploadPartCopy sources) and require S3 Bucket Keys under SSE-KMS.

A10 — Backpressure and ENOSPC truthfulness in lite: track dirty backlog against PVC headroom and refuse WRITE/CREATE with NFS4ERR_NOSPC while headroom-minus-reserve is exhausted (the errno applications actually handle, delivered before hard-full — F55 says EIO makes postgres PANIC); map ENOSPC→NoSpc and EDQUOT→DQuot in handle_write/handle_commit (the ds/server.rs:1185-1197 fix the MDS lane never got); reserve state.db headroom (small separate PVC or released ballast file) so the eviction-confirmation write can never be starved by the very fullness it exists to relieve, plus an eviction-trigger watermark (~85%); serve real statvfs-backed SPACE_* attributes for tiered exports (df currently reads ~8 EiB); hydration admission refuses when object size exceeds free-minus-reserve, answering DELAY when eviction can plausibly free space.

A11 — Fold the economics gate's five mandatory knobs into the design text as requirements: per-file flush-interval floor ~60s with on-close as flush-eligibility not flush-now (caps the fsync-churn pathology, $6,480/mo uncapped); merged clean-run UploadPartCopy coalescing contiguous clean parts up to the 5 GiB copy-part limit (collapses the large barely-dirty-file fan-out from ~$8,280/mo/file to ~$1.73); the A4 quiescence guard; the A9 lifecycle rule in bootstrap; IA lifecycle gating (only ≥30-day-untouched objects, gated on observed hydration rate) plus an IA copy-source guard — UploadPartCopy from an IA source pays $0.01/GB retrieval on every CLEAN byte and silently inverts the saving. Additionally: part size chosen per generation as max(threshold, ceil(size/10000)) on a fixed grid, persisted in the generation row; 5 TiB enforced as a per-file limit at write time with a clear error; frame UploadPartCopy's value honestly as hub-bytes/CPU savings, not S3-bill savings.

A12 — Specify the observability surface and the DR manifest. A DataPathMeter-style tier meter with its own silent-when-idle reporter: dirty bytes/files + oldest-unflushed age, flush inflight/failed/412 count, hydration inflight/latency/DELAY-answers, evicted files/bytes + eviction refusals by reason, PVC headroom with time-to-full WARN, outstanding MPU count/age, epoch lease age; hydration/evicted-serve lanes excluded from the F68a mds_data_bytes WARN input (so the fleet's trained-on corruption signature stays meaningful when the full posture returns). DR: write a small manifest object at every flush barrier — barrier seq plus per-file {gen, ETag, mode, uid, gid, mtime, type, symlink target} — which is simultaneously the metadata checkpoint, the RPO record, and the restore driver; stamp mode/uid/gid/mtime as object metadata; rewrite §8's DR sentence to 'CAS + manifest-driven restore + consumer remount' and enumerate what the tier declines to round-trip (hard links, sockets/FIFOs, sparseness).

A13 — Object store behind a trait from day one (added 2026-08-15 after the
user's Azure Blob question). Only generation assembly is backend-specific;
everything else (interval log, eviction, hydration, ingestion, epoch) is
backend-neutral. Trait ops: put_whole, compose_generation(dirty_ranges,
clean_ranges, if_match), get_whole_if_match, head, list, epoch
acquire/renew/release. S3 backend: MPU + UploadPartCopy + conditional-PUT
epoch per A6/A8. Azure Blob backend (second): Put Block / Put Block List with
committed-block REUSE (clean parts are referenced, not copied — cheaper than
UploadPartCopy), Put Block From URL for foreign-written previous generations,
no 5 MiB part floor, and NATIVE BLOB LEASES for the epoch — a real TTL'd
lease, strictly better than the S3 CAS epoch and it directly answers A8's
liveness concern. GCS later: compose + generation preconditions. Do not chase

gateway's caveats.

## Economics (gate: CONDITIONAL GO)

CONDITIONAL GO, adopted as ruled. The tier is storage-price arbitrage and it works: lite+S3 beats every always-hot alternative by ~2.7-3.3x at the target 4-5% working sets (W1 ~$148-166/mo vs gp3 $440-492; W2 ~$300-315 vs $880-983), requests stay <6% of the bill at sane cadences, and break-even sits at ~47% (Standard) / ~56% (IA-blended) working-set fraction — an order of magnitude above where the workloads live. But the GO is real only with the five knobs, so they are promoted from tuning advice to design requirements (amendment A11): without the flush floor, merged clean-run copies, quiescence guard, bootstrap MPU-abort lifecycle rule, and IA copy-source guard, realistic scenarios exist where request or retrieval costs dominate ($6,480/mo fsync churn; $8,280/mo/file copy fan-out; $153/mo silent IA retrieval on clean bytes) — and W1's sqlite/git WAL churn is literally the fsync-churn scenario, not a contrived one. Two review findings feed back into the gate's model: the part-size amplification curve (5 MiB floor rising to 500+ MiB/part near the 5 TiB ceiling — one dirty 4 KiB page re-uploads a whole part) and the Versioning-ON noncurrent tail (A9) are first-class cost inputs the published numbers must carry. Two loose ends before publishing any comparison: verify Amazon S3 Files pricing against the official sheet (secondary sources conflict; flint wins under both readings), and note the MPU-leak findings independently confirm the gate's lifecycle-rule knob from the correctness side. Gate (b) remains open but changes shape under amendment A5: with DELAY-based hydration replacing in-RPC READ holds, the rig measurement is now Linux-client NFS4ERR_DELAY retry/backoff behavior across multi-minute hydrations (plus permit-non-consumption), not raw READ-hold tolerance — measure that before eviction/hydration ships (implementation step 9).

**Agreed numbers (the two models reconciled):** Adopted (A's binary-GB method where they differ): W1 (5 TiB, ~4% hot): ~$148-166/mo all-Standard ($117.76 storage + $24 hub gp3 PVC ~300GB + $4-24 requests by cadence), ~$111/mo with 30-day IA lifecycle. W2 (10 TiB, ~5% hot): ~$300-315/mo all-Standard ($235.52 + $60 PVC + $4-19 requests), ~$238-250/mo with IA (incl. $16-24/mo IA hydration retrieval — the one place IA bites). Baselines: all-hot gp3 $440-492 (W1) / $880-983 (W2) — lite+S3 is 2.7-3.3x cheaper; EFS ~$376-459 (W1) / ~$414 (W2, dirty-bytes-consistent) — loses on Elastic throughput write fees at any churn; Amazon S3 Files $225-426 (W1) / $425-579 (W2) — flint wins under both models' conflicting price readings; JuiceFS within ~$30-50/mo of flint — a cost wash, interop (native whole-file bucket vs 4 MiB chunk soup) is the real differentiator. Break-even working-set fraction vs gp3: ~47% on Standard, ~56% IA-blended (B's PVC-inclusive formula); workloads sit at 4-5%, an order of magnitude inside. Both models agree: UploadPartCopy saves ~$0 on the S3 bill itself (COPY bills at PUT rate, in-region bytes free both ways) — its value is hub bytes/CPU (95% less data through the MDS), and it must be framed that way in the design doc. Requests stay <6% of the bill at every sane cadence; recommended default 60s flush cadence with quiescence.

**The five mandatory knobs (now requirements, per A11):**
- Per-file flush-interval floor (~60s): on-close becomes flush-eligibility, not flush-now; caps any continuously-hot file at ~$0.22/mo and defuses the fsync-churn pathology (uncapped: $6,480/mo for 50 agents x 10 closes/s — W1's sqlite/git WAL churn is exactly this workload)
- Merged clean-run UploadPartCopy (coalesce contiguous clean parts up to the 5 GiB copy-part limit): collapses the large barely-dirty-file copy fan-out from ~$8,280/mo/file at 60s cadence to ~$1.73/mo/file
- Quiescence guard: never flush a file whose write stream is still advancing (or still open) — removes W2's only cadence-driven bump (~$19-48/mo of intermediate half-written generations at 60s cadence)
- AbortIncompleteMultipartUpload lifecycle rule (1-7 days) created in bucket bootstrap, not left as operator advice — orphaned MPU parts are invisible to LIST and bill as storage forever; with the rule, exposure <$2/mo
- IA lifecycle gating + IA copy-source guard: transition only >=30-day-untouched (effectively never-rewritten) objects, and flush must refuse or first-restore an IA copy-source — UploadPartCopy from IA pays $0.01/GB retrieval on every clean byte ($153/mo on W2, silently inverting the IA saving); additionally gate lifecycle adoption on observed hydration rate (W2 IA retrieval at 5x hydration = $120/mo, at which point Standard-only is cheaper)

## Implementation order

1. Mutation-capture module (A2) with the change-counter-census hooks in all seven MDS lanes, the whole-file-dirty invariant, and the debug assertion — pure local code, no S3, testable with fsx-style drills on the Linux rig; this is the foundation every confirmed 'stale bytes published' critical stands on, so it ships and soaks first.
2. Durable dirty bit + flush-intent rows + startup reconciler skeleton in the sqlite backend (A3, A6's intent row), following the truncate_pending pattern — crash-restart drills (kill -9 mid-write, restart, assert bit-set files re-upload whole and clean files are provably skippable) close the two crash-restart criticals before any flush logic exists.
3. Per-file write gate + flush single-flight + FdCache evict-by-path/ino (A4, A5's cache primitive) — the exclusion primitive the whole tier depends on, drill: concurrent pwrite storm vs gate drain, assert no torn snapshot.
4. S3 client layer with conditional publish (If-Match PUT/Complete, If-None-Match:* creates), metadata stamps + CRC64NVME, HEAD-based 412 arbitration, MPU abort-on-failure, and the bucket bootstrap checks (versioning posture, lifecycle rule, IAM probe) (A6, A9) — tested against real S3, including induced 412s in both self-torn and genuinely-foreign flavors; the tier meter skeleton (A12 counters) lands here and grows with each subsequent step.
5. Flush pipeline: intervals → part layout (per-generation part sizing, merged clean-run copies, 5 TiB limit), flush floor + quiescence gating, whole-file and sub-threshold PUT paths (A11) — first end-to-end generation publishes; economics counters validate the gate's request-cost model against a live bill.
6. Identity-keyed rows + note_rename/note_remove hooks + tombstones + LINK refusal (A7) — must precede any import-refresh or eviction, since both consume its invariants; drill: git workload (tmp-write+rename storm) flushing without a single false 412.
7. Epoch object with lease heartbeat, self-recognition, takeover MPU abort-sweep, self-fencing (A8) — drill: kill the hub mid-flush, restart (must resume without operator CAS), then true takeover with an in-flight MPU (deposed Complete must fail NoSuchUpload).
8. Backpressure + ENOSPC truthfulness: NOSPC admission, errno mapping, state.db reserve, watermarks, statvfs SPACE_* (A10) — before eviction exists, so the full-PVC wedge can never be entered by the relief valve's own bookkeeping.
9. RIG GATE: measure Linux-client NFS4ERR_DELAY retry behavior across multi-minute simulated hydrations (open gate (b), re-scoped per A5) — a hard go/no-go before any destructive code ships.
10. Eviction (A5's marker-before-truncate order, A4's full precondition set, startup reconciler completion, capacity-return-after-confirmation) — deliberately last-but-one: it is the only operation that destroys local bytes, and every guard it depends on (bit, gate, identity keys, publish guards) is now drill-proven; drill: crash at every step boundary of the state machine.
11. Hydration (in-place restore, DELAY parking off the pipeline permits, coalescing, hydrate-first WRITE barrier, admission) (A5, A10) — drill: hydration under concurrent open/READ/WRITE with the F17b/c fd paths, crash mid-restore, ENOSPC mid-GET.
12. Import-refresh verb (consumes A7's tombstones) + DR manifest writer and manifest-driven restore (A12) — finish with a full DR drill: destroy the PVC, CAS + rebuild from bucket, assert the restored tree's POSIX fidelity against the manifest and that the RPO is readable from the bucket alone.
