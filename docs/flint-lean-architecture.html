Flint-lean — plain files, one bucket

1 / 7 · architecture

The third front end over the flint bucket format, split out of the flint-fuse architecture doc: if the workspace fits on disk, no interception is needed at all. Materialize plain files at pod start, publish changed files at a boundary with an unprivileged syncer — a worker pod the CSI node driver starts beside the tenant, never a container injected into it — and give writers outside the pod a stateless gateway that is, since 0.2, a library. Most of FUSE's value at a fraction of its risk surface — same bucket format, same engine.

One dialect — the S3 surface, three placements

2 / 7 · protocol

The decision of record: every REST surface in the system speaks the S3 dialect — the hub's file API converges onto it, the gateway serves it, and direct-mode non-mount access (lean and FUSE alike) is plain S3 against the bucket. One library, three placements; the consistency contracts say which view a client is reading.

Boundary verbs — the agent says when

3 / 7 · architecture · shipped 2026-08-26

Pages 1–2 describe publishing at cadence: an mtime/size scan on a timer. That is still the default, and it is still the whole story for a workspace nobody is watching. What it could not express is a coherent point — “these files, together, now” — so an agent finishing a unit of work had no way to say so and no way to learn when its bytes were durable. The boundary verbs are that sentence, written as files in the workspace the agent already has. Nothing new is mounted, no port is opened, and a workspace that ignores them pays nothing: measured at 20 bucket requests per 22 s idle with the verbs off and 20 with them on.

Does it fit? — the workflow lean is for

4 / 7 · use case · sizing

Lean is not a general filesystem and does not try to be. It is for one agent, one workspace, one writer, a workspace that fits on disk — the harness shape: clone-ish tree of code and artifacts, an agent that reads and writes it locally at full speed, and a durable point somebody else can read when the work is done. Everything below is the boundary of that claim, in measured numbers, so the answer to “will this work for us” is arithmetic rather than opinion.

Outside the pod — the gateway is a crate

5 / 7 · architecture · shipped 2026-09-12

A UI, a reviewer, a backend serving a thousand workspaces: none of them is in the pod, and none of them may touch the agent’s tree or edit the manifest. flint-lean-gateway is the door for them, and since 0.2 it is a library — a backend depends on the crate and calls the verbs in-process; the flint-lean-gateway binary is main around the same router, so there is one implementation and one set of refusals. The door talks to the bucket, never to a syncer: it can run on another cluster, or on none.

What the syncer learned — integrity, scope, throughput, arbitration

6 / 7 · architecture · 2026-09-04 → 2026-09-12

Pages 1–4 describe the protocol. This page is what changed in the syncer once it met real buckets, real nodes and the formal model: every fetched byte is verified against a CRC the client computed, a checkout can be a scope rather than the whole tree, the read and publish paths lost the copies, the lock and the double read that bounded them, and a reader no longer stands in the writer’s queue. Every number is a range over reps from a drill committed under lean/e2e/perf/results/; the four-door comparison against passthrough and the CLI is measured separately, in the door-drill results there.

Git on a lean workspace — two jobs, two paths

7 / 7 · use case · collaboration

The obvious question once several agents share a repo: how do they integrate? The answer is that they do not integrate through flint-lean at all. Use plain git against a real git host, and let flint-lean keep the workspace durable. Two mechanisms, two network paths, two different jobs — and they never touch, which is exactly why nothing special is needed to make them coexist. Full guide: docs/flint-lean-git-workflow.md.
